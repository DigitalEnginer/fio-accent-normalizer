# Техническое досье проекта автоматизации ударений

## 1. Краткое описание проекта

Проект автоматизирует нормализацию отдельных частей ФИО и постановку ударений для синтеза речи.

На вход поступает одна строка:

- имя;
- фамилия;
- отчество.

Полное ФИО системе не передаётся. Например:

```text
саңдк → сағынд+ық
аблае → абл+ай
```

Система выполняет две разные задачи:

1. GPT распознаёт строку и исправляет очевидные ошибки.
2. Локальная обученная модель расставляет ударения.

Результат не сразу отправляется в рабочую базу. Сначала он попадает в пачку на проверку оператором.

## 2. Общая архитектура

```text
Рабочая БД / временный ручной ввод
              ↓
Первичная нормализация строки
              ↓
GPT: распознавание и исправление написания
              ↓
Локальная модель: постановка ударения
              ↓
Автоматическая проверка формата результата
              ↓
Пачка операторской проверки
      ┌───────┼────────┐
    Готово  Проверить  На удаление
      └───────┼────────┘
              ↓
Подтверждение всей пачки
              ↓
Журнал результатов
              ↓
Будущая интеграция с рабочей БД
```

Главный архитектурный принцип: GPT не отвечает за окончательное решение в одиночку. Исправленные и сомнительные строки выводятся оператору.

## 3. Что делает каждый компонент

### GPT API

GPT используется как интеллектуальный корректор написания.

Он возвращает одно из решений:

- `KEEP` — строка может быть настоящим именем, её написание сохраняется;
- `CORRECT` — обнаружена вероятная ошибка или требуется транслитерация;
- `UNKNOWN` — строка явно не похожа на часть ФИО.

GPT обрабатывает:

- пропущенные буквы;
- лишние буквы;
- перестановку букв;
- неправильную раскладку;
- ввод латиницей;
- очевидные неименные слова;
- технический мусор;
- редкие казахские, русские и другие имена.

GPT не расставляет окончательное ударение. После его решения строка передаётся локальной модели.

Ответ GPT запрашивается в строгом JSON-формате:

```json
{
  "decision": "CORRECT",
  "normalized": "сағындық",
  "confidence": "high",
  "unknownKind": "none"
}
```

Сейчас используется модель `gpt-5.6-sol` через Responses API:

- reasoning effort: `medium`;
- verbosity: `low`;
- строгая JSON Schema;
- temperature вручную не задаётся;
- до трёх попыток при временных ошибках API.

GPT-5.6 Sol сейчас не поддерживает fine-tuning. Поэтому GPT не обучался на наших данных: собственное обучение выполнено для локальной модели ударений. Актуальные характеристики и цены приведены в [официальной документации GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol).

### Локальная модель ударений

Это собственная небольшая символьная Transformer-модель на PyTorch.

Модель анализирует слово посимвольно и решает:

- перед какой гласной поставить `+`;
- требуется одно или два ударения.

Она не ищет имя в справочнике, а предсказывает позиции ударения по структуре слова. Поэтому может работать с ранее не встречавшимися именами.

| Параметр | Значение |
|---|---:|
| Тип | Character-level Transformer Encoder |
| Количество параметров | 157 348 |
| Размер checkpoint | около 630 КБ |
| Размер словаря символов | 45 |
| Максимальная длина | 32 символа |
| Скрытая размерность | 96 |
| Attention heads | 4 |
| Transformer layers | 2 |
| Feed-forward размер | 192 |
| Dropout | 0,15 |
| Выход №1 | вероятность ударения для каждого символа |
| Выход №2 | выбор одного или двух ударений |
| Среда выполнения | PyTorch, CPU |

Модель маленькая и может работать на обычном офисном ноутбуке без видеокарты.

### RUAccent

RUAccent оставлен как дополнительный резервный компонент для ограниченного набора распространённых русских имён.

Система не пытается окончательно определить национальность человека. Окончания `-ов`, `-ова`, `-ович` сами по себе не считаются достаточным признаком русского имени, потому что такие формы распространены и среди казахстанских ФИО.

Основной маршрут ударений идёт через нашу локальную модель. RUAccent используется только как узкий fallback, если основная модель не смогла обработать строку и она совпадает с известной русской формой.

## 5. Что означают метрики

### Exact accuracy — 90,78%

Из 94 181 проверочной строки модель полностью правильно воспроизвела ударения в 85 496 строках.

Ошибок полного совпадения:

```text
94 181 − 85 496 = 8 685
```

Полное совпадение означает, что выбрано правильное количество ударений и каждое ударение стоит именно перед правильной гласной.

### Stress-count accuracy — 98,98%

В 98,98% случаев модель правильно определяет, сколько ударений требуется: одно или два.

Это не означает, что позиции всех ударений правильные. Модель может правильно определить, что нужно одно ударение, но поставить его не перед той гласной.

### Корректная формулировка метрики

> На отложенной исторической выборке локальная модель достигла 90,78% полного совпадения с размеченными человеком результатами и 98,98% точности определения количества ударений.

Нельзя утверждать, что система уже имеет 90,78% точности в промышленной эксплуатации. Промышленная точность пока не измерена на независимом потоке новых записей.

Кроме того, финальная метрика рассчитана при текущей стратегии разделения данных. Перед полноценным внедрением желательно сформировать отдельный закрытый gold test, сгруппированный по исходному имени, чтобы одинаковые или близкие формы не попадали одновременно в обучение и проверку.

## 6. Логика обработки одной строки

Например, поступает:

```text
саңдк
```

Процесс:

1. Строка приводится к нижнему регистру.
2. Удаляются пробелы по краям.
3. Проверяются Excel-ошибки и строки без букв.
4. GPT определяет: `CORRECT → сағындық`.
5. Исправленная форма отправляется локальной модели.
6. Модель возвращает `сағынд+ық`.
7. Проверяется формат результата.
8. Поскольку GPT изменил написание, строка попадает в раздел «Требует внимания».
9. Оператор проверяет строку.
10. После подтверждения пачки результат записывается в журнал.

Автоматическая проверка требует, чтобы:

- ответ состоял из одной строки;
- использовался нижний регистр;
- не было пробелов;
- `+` находился непосредственно перед гласной;
- не было запрещённых символов.

## 7. Политика исправлений и удаления

В этом проекте ошибка удаления считается дороже ошибки сохранения.

Если ошибочно удалить одну часть ФИО, оставшиеся части могут стать бесполезными, и звонок клиенту не состоится.

Поэтому:

- редкое, но правдоподобное имя стараемся сохранить;
- незнакомая строка не считается мусором автоматически;
- сомнительный `UNKNOWN` может быть возвращён локальной моделью на проверку;
- очевидное слово вроде `apple`, `dent`, служебные данные и технический мусор могут стать кандидатами на `NULL`;
- окончательное решение доступно оператору.

`UNKNOWN` внутри интеллектуального конвейера и `NULL` для базы — разные понятия:

- `UNKNOWN` — модель не признала строку частью ФИО;
- `NULL` — бизнес-решение о том, что должно быть записано в БД.

Сейчас в локальном журнале строки из раздела «На удаление» записываются текстовым значением `NULL`. Это ещё не физический SQL `NULL` и не удаление строки.

Перед подключением рабочей БД необходимо согласовать один из вариантов:

- записывать SQL `NULL` в поле имени;
- устанавливать отдельный статус `invalid_name_part`;
- записывать результат в промежуточную таблицу;
- хранить исходное значение и признак исключения.

Предпочтительный вариант — не удалять исходные данные физически, а использовать статус и аудит.

## 8. Пакетная проверка оператором

После обработки строка сразу добавляется в открытую пачку.

В пачке есть три категории:

- «Готовые» — система не обнаружила существенных проблем;
- «Требуют внимания» — GPT изменил написание, предложил исправление или локальная модель не уверена;
- «На удаление» — кандидат на `NULL`.

Оператор может:

- изменить результат прямо в текстовом поле;
- переместить отдельную строку в «Готовые»;
- вернуть её в «Требует внимания»;
- отправить её «На удаление»;
- сделать это без изменения остальных строк;
- подтвердить всю пачку одной кнопкой.

На каждое имя не требуется отдельный approve.

При подтверждении сервер повторно проверяет все строки. Непустая строка без корректно расположенного `+` не может быть подтверждена как готовая.

Максимальный размер пачки на уровне API сейчас — 200 строк. В браузере обработка выполняется тремя параллельными рабочими запросами.

## 9. Журнал результатов

После подтверждения пачки результаты переходят в локальный журнал.

Журнал хранит:

- исходную строку;
- итоговый результат;
- источник обработки;
- название модели;
- дату и время.

Для пачек дополнительно сохраняются:

- номер пачки;
- статус `reviewing` или `approved`;
- общее количество строк;
- время создания;
- время подтверждения;
- исходное значение;
- предложенное значение;
- финальное значение;
- категория строки;
- причина внимания;
- модель;
- признак ручного редактирования;
- будущий внешний ID записи.

Журнал нужен для:

- аудита;
- поиска ошибок;
- сравнения версий моделей;
- формирования новых проверенных обучающих данных;
- восстановления истории решения;
- будущего контроля качества операторов.

Для промышленной версии в журнал желательно добавить:

- ID оператора;
- версию GPT-промпта;
- решение GPT и confidence;
- версию локального checkpoint;
- время обработки;
- OpenAI request ID;
- старое и новое значение из рабочей БД;
- причину ручного изменения.

## 12. Защита API-ключа

API-ключ не хранится во frontend-коде и не отправляется браузеру.

В локальной версии:

- ключ загружается из `.env.local`;
- OpenAI proxy доступен только через `127.0.0.1`;
- CORS разрешён только для `localhost:3000`;
- ответы не кэшируются;
- максимальный HTTP body — 256 КБ;
- одна пользовательская строка ограничена 120 символами;
- запрос к OpenAI имеет timeout 25 секунд;
- временные ошибки `408`, `409`, `429` и `5xx` повторяются до трёх раз.

Перед промышленным внедрением обязательно:

- хранить ключ в корпоративном secrets manager;
- ротировать ключ, если он когда-либо публиковался в чате, скриншоте или логе;
- добавить аутентификацию и роли;
- использовать HTTPS;
- ограничить доступ по внутренней сети;
- запретить запись персональных данных в технические логи;
- согласовать обработку данных внешним API с отделом информационной безопасности.

## 13. Отказоустойчивость

Система разделена на независимые этапы.

Если GPT недоступен:

- строка не должна автоматически удаляться;
- пачка должна получить ошибку или статус ручной проверки;
- возможен повторный запуск.

Если локальная модель недоступна:

- результат не считается готовым;
- строка возвращается без автоматического подтверждения;
- она попадает в раздел внимания.

Если приложение выключилось:

- уже сохранённая пачка остаётся в локальной БД;
- обучение не возобновляется автоматически с середины эпохи, если checkpoint не был сохранён;
- для production нужен systemd, Docker, Windows Service или другой менеджер процессов.

## 14. Стоимость

Локальная модель не имеет стоимости за каждый API-запрос. Она использует CPU компании.

Платная часть — GPT API.

Текущая цена GPT-5.6 Sol:

- input: $4 за 1 млн токенов;
- cached input: $0,40 за 1 млн токенов;
- output: $20 за 1 млн токенов.

Цены могут измениться, поэтому перед расчётом бюджета нужно проверять [официальную страницу модели](https://developers.openai.com/api/docs/models/gpt-5.6-sol).

Формула:

```text
стоимость =
input_tokens / 1 000 000 × $4
+
output_tokens / 1 000 000 × $20
```

Сейчас точная стоимость одной строки не измерена. Нельзя называть её руководству без замера на реальной пачке, поскольку учитываются системная инструкция, JSON-ответ и reasoning tokens.

Для бюджета нужно обработать, например, 10 000 реальных строк и зафиксировать:

- общее количество токенов;
- стоимость;
- среднюю задержку;
- долю GPT-исправлений;
- долю ручной проверки;
- долю `NULL`.

## 17. Как система будет подключена к рабочей БД

Предлагаемый безопасный вариант:

1. Получать пачку записей только на чтение.
2. Вместе со строкой получать внешний ID записи.
3. Обрабатывать только одну часть ФИО.
4. Сохранять результат в промежуточную таблицу.
5. Показывать пачку оператору.
6. После подтверждения записывать изменения транзакцией.
7. Хранить старое значение, новое значение, модель и оператора.
8. Не удалять исходную запись физически.
9. При ошибке откатывать всю транзакцию.
10. Повторная обработка должна быть идемпотентной по external ID.

## 18. Как модель будет улучшаться

```text
Новые строки
    ↓
Предсказания модели
    ↓
Исправления оператора
    ↓
Проверенная gold-база
    ↓
Периодическое переобучение
    ↓
Сравнение старой и новой версии
    ↓
Canary-тест
    ↓
Внедрение или откат
```

Нельзя обучать модель прямо на каждом операторском изменении без проверки. Иначе человеческая ошибка сразу попадёт в модель.

Правильный вариант:

- собирать исправления;
- проверять их;
- версионировать датасет;
- обучать новую версию отдельно;
- сравнивать на неизменяемом тестовом наборе;
- внедрять только при улучшении ключевых метрик;
- сохранять предыдущий checkpoint для отката.

## 19. Готовые ответы на технические вопросы

### Вы обучали GPT?

Нет. GPT используется через API и строгий промпт. Мы обучили собственную локальную Transformer-модель для постановки ударений.

### Почему не использовать только GPT?

GPT хорошо исправляет написание, но его ответы стоят денег, зависят от внешнего API и могут меняться. Локальная модель дешевле, воспроизводима и обучена на наших исторических данных.

### Почему не использовать только локальную модель?

Локальная модель получает уже очищенную строку и специализируется на ударениях. Она не предназначена для надёжного восстановления пропущенных букв, раскладки и определения служебного мусора.

### Какова точность?

90,78% полного совпадения ударений и 98,98% правильного количества ударений на отложенной исторической выборке. Это ещё не производственная метрика.

### Почему всё равно нужен оператор?

Ошибка удаления может привести к недозвону клиенту. Кроме того, около 9,22% проверочной выборки не совпали полностью с разметкой. Оператор контролирует рискованные изменения.

### Система работает только с казахскими именами?

Нет. Она принимает отдельные части ФИО разных национальностей. Основная модель обучена на реальных исторических данных Казахстана, где встречаются казахские, русские, уйгурские и другие формы. Система не определяет национальность человека.

### Может ли быть два ударения?

Да. У модели есть отдельная выходная голова, которая определяет необходимость одного или двух ударений.

### Может ли она обработать имя, которого никогда не было в базе?

Да. Модель работает посимвольно, а не только по словарному совпадению. Но точность для полностью новых форм должна быть отдельно проверена на grouped gold test.

### Почему используется `+`?

Это формат, который ожидает используемый синтезатор речи: знак ставится непосредственно перед ударной гласной.

### Может ли система удалить настоящее имя?

Автоматически физически удалить запись она не должна. `UNKNOWN` является кандидатом на `NULL`, который оператор может вернуть в проверку или готовые.

### Можно ли откатить результат?

В локальной версии хранится журнал. Для production потребуется полноценный аудит старого и нового значения и транзакционный rollback.

### Работает ли система без интернета?

Локальная модель ударений — да. GPT-коррекция — нет. При отсутствии GPT строка должна переходить в ручную проверку.

### Хватит ли офисного ноутбука?

Для обучения текущей небольшой модели хватило: четыре эпохи заняли около 1 часа 47 минут на CPU. Для значительно более крупных языковых моделей ноутбука будет недостаточно.

### Где хранятся персональные данные?

Сейчас используется локальная тестовая БД. В production необходимо согласовать хранение, сроки удаления, доступ и передачу отдельных частей ФИО во внешний API.

### Какова стоимость обработки?

Локальная модель не тарифицируется по запросам. Точную стоимость GPT нужно измерить на реальной контрольной пачке; сейчас нельзя честно назвать стоимость одной строки.
